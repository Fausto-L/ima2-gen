# Phase 130 — Provider QA + MCP smoke + Node 성능 + 060 closeout

이 phase는 새 기능을 구현하는 단계가 아니다. 070의 3-provider 요소 검수, 승인된
Runway MCP 1건 smoke, 080의 100-node 성능 프로파일, 이미 배선된 060의 잔여
실증을 같은 증거 규약으로 닫는다. 수치나 provider 계약이 실패하면 실제값을
남기고 종료한다. 이 phase에서 virtualization, 경고 전파, 테스트 시트 endpoint,
Gemini video routing을 추가하지 않는다.

## 재검증된 기준선

- 070은 같은 character element를 GPT/Gemini/Grok에서 각 1회 생성해 얼굴·복장
  drift, 참조 상한, notes 비노출을 검수하도록 요구한다
  (`070_elements.md:646-652`, `095_current_status.md:58-67`).
- classic image의 element 주입은 provider 해석 뒤 실행되며
  `lib/generatePipeline.ts:115-170`에서 element refs와 notes를 합성한다.
- image provider 값은 GPT OAuth `oauth`(기본값), Gemini API `gemini-api`, Grok
  `grok`이다 (`lib/providerOptions.ts:4-5`, `:22-31`, `:34-45`). Gemini는
  Gemini API key 또는 Vertex service account가 있어야 ready다
  (`routes/models.ts:149-167`, `routes/keys.ts:73-96`).
- element image 상한은 GPT 6, Gemini 6, Grok 4 refs다
  (`lib/elementCompiler.ts:57-60`). `droppedRefs`는 compiler 결과에 존재하지만
  (`:48-54`, `:136-194`) 현재 classic pipeline은 이를 사용자 경고로 전달하지
  않는다. 경고가 보이지 않으면 PASS로 간주하지 않고 실제 상태를 기록한다.
- Element test-sheet 버튼은 현재 생성 endpoint가 아니라 unavailable toast에
  연결돼 있다 (`ui/src/components/assets/AssetsWorkspace.tsx:116`,
  `ui/src/i18n/ko.json:1730`). 추가 구현이나 숨은 4회 생성을 하지 않는다.
- Runway 연결은 `POST /api/mcp/providers/runway/connect`, 생성은
  `POST /api/mcp/generate`이고 202 뒤 `/api/events`의 같은 `requestId` terminal
  event를 기다린다 (`routes/mcpConnections.ts:120-127`,
  `routes/mcpMedia.ts:223-243`, `:326-363`, `routes/events.ts:26-68`).
- 로컬 `~/.ima2/mcp/runway.json`은 mode 0600의 opaque credential이고 현재
  server status는 `disconnected`다. access/refresh token은 어떤 증거에도 복사하지

  upstream이 반환한 확정 expiry로 취급하지 않는다.

- `NodeCanvas`의 `ReactFlow`에는 `onlyRenderVisibleElements`가 지정돼 있지 않아
  현재 @xyflow 기본값 `false`, 즉 모든 node가 mount되는 기준선이다
  (`ui/src/components/NodeCanvas.tsx:117-157`).
- 060 image preset 경로는 UI compile → `appliedPresetIds` 전송 → route 정규화 →
  image meta/sidecar → XMP 순서 보존·중복 제거까지 배선돼 있다
  (`ui/src/store/storePresetImpl.ts:13-40`, `storeGenImpl.ts:268-284`,
  `routes/generate.ts:6-10`, `lib/generatePipeline.ts:404-430`,
  `lib/imageMetadata.ts:19-21`, `:40-77`).
- `tests/preset-xmp-roundtrip.test.ts:25-55`는 source `xmp`, dedup, 선택 순서를
  포함한 5개 계약이다. 반면 현재 direct video route는 Grok/Grok API만 허용하고

## A. 070 — 동일 element 3-provider 수동 QA

### 입력 고정

`assets/070/element-fixture.json`에 token 없는 입력 명세만 남긴다.

```json
{
  "elementId": "<actual-id>",
  "elementKind": "character",
  "refOrder": ["front", "side"],
  "basePrompt": "<same raw user prompt>",
  "providers": ["oauth", "gemini-api", "grok"]
}
```

- 같은 element ID, 같은 ref 순서, 같은 raw user prompt, 같은 size/aspect를 쓴다.
- front와 side ref를 최소 1장씩 포함한다. composer의 별도 ref는 넣지 않아 element
  capacity만 비교한다.
- raw prompt에는 element notes를 복사하지 않는다. UI에서 element를 선택해
  `elementIds`로만 전달한다.
- provider별 model은 `/api/models`가 반환한 ready lane의 현재 기본 image model을
  기록한다. Gemini는 `provider: "gemini-api"`와 ready credential을 사용한다.

### 실행 순서

1. element 상세에서 ID, refs 순서, notes SHA-256만 기록한다. notes 원문은 결과
   비교 문서에 복제하지 않는다.
2. `oauth` → `gemini-api` → `grok` 순서로 provider를 바꾸고 각각 정확히 한 번
   생성한다. 매 요청의 requestId, model, 시작·종료 시각, terminal 상태를 남긴다.
3. 각 원본과 sidecar를 `assets/070/results/{gpt-oauth,gemini-api,grok}/`에 복사한다.
   sidecar에서 `provider`, `model`, `refsCount`, `elementIds`, `userPrompt`,
   `prompt`, `warnings`만 sanitized 추출한다.
4. 얼굴은 눈·코·입 비율, 헤어라인, 피부 특징을 기준으로 `none/minor/major` drift,
   복장은 색·실루엣·패턴·액세서리를 같은 척도로 판정한다.
5. 기대 refs는 GPT/Gemini 최대 6, Grok 최대 4와 대조한다. 초과 ref가 있는
   fixture라면 dropped count/reason과 visible warning을 확인한다. compiler 예상과
   실제 refsCount가 다르거나 visible warning이 없으면 `FAIL`과 함께 기록한다.
6. history의 raw user prompt와 생성 sidecar `userPrompt`에 element notes fragment가
   들어가지 않았는지 확인한다. notes가 한 번이라도 노출되면 `FAIL`이다.

### 4종 비교판

추가 생성 없이 세 원본으로 다음 파일을 만든다.

1. `assets/070/test-sheet-01-full-frame.png` — front/side refs + 3-provider 전신.
2. `assets/070/test-sheet-02-face-crops.png` — 동일 배율 얼굴 crop.
3. `assets/070/test-sheet-03-outfit-crops.png` — 동일 배율 복장 crop.
4. `assets/070/test-sheet-04-capacity-history.png` — refsCount/warning/history 표.

product의 “Run test sheet” 자체는
`assets/070/test-sheet-product-status.md`에 `BLOCKED — unavailable toast`로 남긴다.
이 phase에서 이를 고치거나 4개 generation을 우회 호출하지 않는다.

### 판정

- `PASS`: 세 provider 모두 done, element ID/refs가 기대대로 적용되고 notes가 raw
  history에 없으며 drift와 capacity 비교 4종 증거가 존재한다.
- `FAIL`: 생성은 끝났지만 drift major, ref count 불일치, warning 비노출, notes
  leakage 중 하나가 확인된다. 실제 결과를 보존한다.
- `BLOCKED`: lane credential/auth/quota/provider 오류로 1회 요청을 완료하지 못했다.
  오류 code/status/requestId를 남기고 재생성하지 않는다.

## B. Runway MCP — 승인된 image smoke 1건

Runway 실행 범위는 `gen-4` **IMAGE 정확히 1건**이다. video smoke, 다른 model
대체, usage를 알 수 없는 추가 시도는 금지한다. connect/catalog/status 확인은
credit을 쓰지 않는 free check로 먼저 끝낸다.

### 절차

1. free check로 `POST /api/mcp/providers/runway/connect`를 호출한다. 이어서
   `GET /api/mcp/providers/runway/status`와
   `GET /api/mcp/providers/runway/models`를 읽어 `connected`, executable catalog,
   image model `gen-4` 존재를 확인하고 sanitized 응답을
   `assets/130/runway-preflight.json`에 저장한다. credential 파일이나 token 값은
   출력하지 않는다.
2. connect/auth가 실패하면 free connect 단계만 최대 한 번 재시도할 수 있다
   (`retryCount <= 1`). 두 번째에도 실패하면 generation submit 없이 즉시
   `BLOCKED`로 기록한다. catalog/status 불일치도 재생성으로 우회하지 않고
   `BLOCKED`다.
3. preflight PASS 뒤 `/api/events`를 열어 원문 SSE를
   `assets/130/runway-events.ndjson`으로 timestamp와 함께 저장한다.
4. 다음 body로 `gen-4` image를 정확히 한 번만 submit한다. generation
   `submitCount`는 어떤 경우에도 `1`을 넘을 수 없으며 video submit은 `0`이어야
   한다.

```json
{
  "provider": "runway",
  "kind": "image",
  "model": "gen-4",
  "ratio": "1:1",
  "prompt": "A single matte ceramic sphere on a neutral gray studio sweep, centered, soft diffused light",
  "requestId": "qa_runway_130_<timestamp>"
}
```

5. HTTP 202 body를 `assets/130/runway-submit.json`에 저장하고 같은 requestId의
   `done` 또는 `error`까지 기다린다. terminal replay가 중복되면 event ID까지
   기록한다.
6. done이면 결과 파일·sanitized sidecar·최종 SSE를 보존하고 파일 decode와 1:1
   dimensions를 확인한다. submit/terminal response payload와 sidecar에서 upstream이
   반환한 usage 또는 cost 값을 찾아 **실제 payload 값과 JSON path**를
   `assets/130/runway-usage.json`에 기록한다.
7. connect/auth 실패 또는 생성 후 usage/cost를 payload에서 기록할 수 없으면
   `BLOCKED`다. usage 부재를 `UNVERIFIED` 성공으로 낮추지 않는다. generation POST는
   재전송하지 않는다. 202 뒤 연결이 끊겨도 동일 requestId SSE replay/status만
   조회하며 새 job을 만들지 않는다.

`assets/130/runway-smoke-result.md`에는 `retryCount <= 1`, image
`submitCount = 1`, video `submitCount = 0`, usage JSON path/value를 함께 기록한다.
preflight에서 막힌 경우에는 image/video submit count를 모두 `0`으로 기록한다.

## C. 080 — 100 imageNodes / 140 edges 성능 프로파일

### 환경과 fixture

- real Chromium/CDP를 사용한다. 기본 runner는
  `/Users/jun/Developer/new/700_projects/agbrowse/node_modules/playwright-core`이고
  browser는 설치된 Google Chrome을 지정한다. 새 Playwright를 설치하지 않는다.
- Vite dev의 `/#node`를 권장한다. source module을 page context에서 import해
  `ui/src/store/useAppStore.ts:169`의 `useAppStore.setState`로 주입할 수 있기 때문이다.
- viewport `1440x900`, DPR `1`, browser zoom 100%, DevTools closed, 같은 machine,
  foreground tab을 고정한다.
- node는 정확히 100개다. `type: "imageNode"`, 10×10 grid,
  `position: {x: col*340, y: row*260}`, stable ID `perf-node-000..099`, empty data를
  사용한다.
- edge는 정확히 140개다. chain 99개(`i -> i+1`)와 deterministic skip 41개
  (`i -> i+10`, `i=0..40`)를 client state에 한 번에 넣는다. 이 fixture는 일부
  target에 incoming edge가 둘이므로 server session save/load를 거치지 않는다.
- 주입 직후 autosave가 fixture를 정규화하거나 사용자 session을 덮지 않도록
  disposable browser profile과 별도 임시 config/server를 사용한다.

### 반복 규약

모든 browser metric은 fixture/reset을 포함한 warmup 2회 뒤 recorded 5회를 수행한다.
sample은 버리지 않고 `assets/080/node-profile.json`에 run별 raw 배열, p50/p95/avg,
환경, gate를 함께 저장한다. p95는 정렬된 배열의 nearest-rank로 계산한다.

1. **Initial render**: `setState({graphNodes, graphEdges, uiMode:"node"})` 직전부터
   `.react-flow__node` 100개와 edge path 140개가 DOM에 나타난 뒤 연속 2 RAF까지를
   잰다. recorded 5개 p95 `<=1000ms`가 guardrail이다.
2. **Pan/zoom**: canvas drag 1200px 왕복 + wheel zoom in/out을 5초 동안 동일 입력
   cadence로 실행하고 RAF delta 전체를 기록한다. run별 평균 FPS `>=30`, 전체
   frame delta p95 `<=33ms`여야 한다.
3. **Interaction**: selection mode에서 deterministic node 50개를 차례로 click하고
   event dispatch 직전부터 selected DOM/state가 반영된 다음 RAF까지 잰다. p95
   `<=50ms`다.
4. **Long task**: `PerformanceObserver({type:"longtask", buffered:true})`를 fixture
   주입 전 설치해 recorded run 종료까지 수집한다. duration `>=200ms`가 하나라도
   있으면 FAIL이다.
5. **Palette search**: app path에서 palette가 노출되면 실제 input을 사용한다.
   현재 `NodeCommandPalette`가 `NodeCanvas`에 연결되지 않은 build라면 Vite page
   context에서 해당 component와 100-command deterministic fixture를 별도 root에
   mount하고 query input→filtered DOM commit까지 30회 잰다. p95 `<=50ms`다.
   fixture 측정은 `integration: false`로 표시하며, product 진입 부재는 별도 FAIL로
   기록한다.
6. **Template instantiate**: 같은 seed ID를 `nodeTemplateStore.instantiate()`로
   30회 실행한다 (`lib/nodeTemplateStore.ts:81-83`, `:107`). 각 call wall time과
   ID uniqueness를 기록하고 p95 `<=500ms`를 적용한다.
7. **Branch transform**: `createBranchGraph()`를 같은 100/140 fixture와 4 variants로
   100 pure runs 실행한다 (`ui/src/lib/nodeBranching.ts:78-110`). p95 `<=10ms`와
   매 run 결과 shape 동일성을 확인한다.
8. **Fit view**: fit-view 후 각 node의 screen bounds가 viewport transform의 계산
   bounds 안에 있고 canvas padding을 벗어나지 않는지 확인한다. full-canvas
   screenshot을 `assets/080/node-profile-1440x900.png`로 남긴다.

해당 세 건 중 하나를 처음부터 element + preset 결합 요청으로 만든다. 별도 7번째
생성을 만들지 않는다.

```bash
ima2 metadata <actual-image-path> --json
```

출력을 `assets/060/image-metadata.json`에 저장하고 다음을 확인한다.

- `source`가 정확히 `"xmp"`다.
- `metadata.presetIds`가 요청 ID와 정확히 같고 선택 순서를 보존한다.
- 중복 ID가 없다.
- sidecar와 XMP의 ID 배열이 같다.

`tests/preset-xmp-roundtrip.test.ts` 5개도 집중 실행해 결과를
`assets/060/preset-xmp-test.txt`에 남긴다. 이 테스트는 실생성 증거를 대체하지
않는다.

## 기록 형식

각 항목은 아래 형식을 그대로 사용한다.

```md
### <ID> — <title>
- terminal: DONE | BLOCKED | NEEDS_HUMAN
- verdict: PASS | FAIL | NOT_RUN
- attempts: <integer>
- retryCount: <integer; Runway free connect max 1>
- submitCount: <integer; Runway image max 1, video 0>
- requestId: <id or n/a>
- startedAt / finishedAt: <ISO-8601>
- input: <sanitized fixture path>
- expected: <contract and gate>
- actual: <measured value/status/error code>
- usage: <provider payload value + JSON path; Runway missing => BLOCKED>
- blocker: <none or exact auth/connect/usage-cost evidence>
- evidence: <relative paths>
- next: <none or follow-up decision; no implementation in Phase 130>
```

`DONE`은 실행과 판정이 끝났다는 뜻이며 반드시 PASS를 뜻하지 않는다. auth/credit,
provider 미지원, product 진입 부재처럼 현재 세션에서 안전하게 해소할 수 없는 것은
`BLOCKED`; 결과 해석이나 예산 확대에 사람 결정이 필요한 경우만 `NEEDS_HUMAN`이다.
Runway는 connect/auth 실패 시 `BLOCKED/NOT_RUN`, image는 생성됐지만 post-hoc
usage/cost를 payload에서 기록할 수 없으면 `BLOCKED/FAIL`로 쓴다. 어느 경우도
free connect retry 1회 또는 generation submit 1회를 초과하지 않는다.

## Phase 130 완료 기준

- 생성 submit은 provider별 예산을 넘지 않고 전체 최대 6건이다.
- A~D 모든 항목에 terminal outcome과 실제 증거 경로가 있다.
- 070의 세 provider 원본, 4종 로컬 비교판, product test-sheet blocker가 구분된다.
- Runway는 free connect/catalog/status를 먼저 확인하고 `gen-4` image만 정확히
  1회 submit한다. connect/auth 실패 또는 post-hoc usage/cost 기록 불가 시
  `BLOCKED`이며, retry count는 최대 1이고 video submit은 0이다.
- node profile은 정확히 100 nodes/140 edges, 2 warmup + 5 recorded와 모든 raw
  sample을 포함한다. gate 미달은 숨기지 않는다.
- 060은 Grok/Gemini video의 실제 지원 상태, raw prompt, sidecar presetIds, image
  XMP source/order를 각각 판정한다.
- 어떤 FAIL/BLOCKED도 이 phase에서 무단 구현 변경이나 추가 생성으로 덮지 않는다.
